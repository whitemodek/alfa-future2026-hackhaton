# Интеграция с ML-модулем

Бэкенд управляет LLM, процессами, бюджетами, журналом, проверкой CSV и публикацией.
Тиммейт отвечает за признаки, модели, разбиения, метрики и качество предсказаний.
Контракт не привязан к регрессии или классификации. ML-тесты здесь не реализуются.

## Вариант 1: Python-инструмент

`run_python(code, timeout_seconds?)` выполняет код новым процессом в каталоге
`task.md`. Между вызовами остаются только файлы. Код может вызывать функции
ML-модуля; каталог решения следует добавить в `sys.path`, если он отличается
от каталога задачи. Не полагайтесь на глобальные переменные предыдущего вызова.

## Вариант 2: модуль `ml_backend.py`

Положите файл в корень рядом с `solution.py`. Инструмент `run_backend` запустит
его как `__main__` в ограниченном дочернем процессе с аргументами:

```text
ml_backend.py /absolute/request.json /absolute/response.json
```

Запрос:

```json
{
  "version": 1,
  "task_path": "/data/task.md",
  "task_dir": "/data",
  "time_budget_seconds": 600,
  "threads": 8,
  "memory_mb": 28000,
  "request": {"action": "experiment", "hypothesis": "..."}
}
```

`request` — свободные параметры ML-части; определите поддерживаемые действия
в модуле. Время и ресурсы верхнего уровня задаёт оркестратор. Рабочая директория
всегда `task_dir`. Пути в исходном условии нужно сопоставлять с реальными файлами.

Ответ: JSON-объект до 64 KB, UTF-8, без NaN/Infinity. Рекомендуемый формат:

```json
{
  "version": 1,
  "status": "ok",
  "candidate_path": "candidate.csv",
  "schema": {
    "columns": ["id", "target"],
    "expected_rows": 100,
    "id_columns": ["id"],
    "numeric_columns": ["target"],
    "sample_path": "sample_submission.csv"
  },
  "score": 0.75,
  "metric": "macro_f1",
  "direction": "maximize",
  "validation_id": "stratified-seed42-split-v1",
  "notes": "Description of experiment and saved model/script"
}
```

Ответ передаётся LLM, которая вызывает `configure_submission` и
`register_candidate`. Сам ответ **не публикует** CSV. Для резервного кандидата
можно не передавать score. Для сравнения нужны одинаковые metric, direction и
validation_id; бэкенд проверяет формат, а достоверность оценки обеспечивает ML.
Финальный refit использует ту же проверенную оценку выбранной конфигурации:
передайте `final: true` в `register_candidate`, чтобы один раз заменить кандидат
при равной оценке. Без этого флага равная оценка не заменяет сохранённый результат.

После первого принятого кандидата схема фиксируется. `sample_path` задаёт
точные столбцы и число строк, а `id_columns` дополнительно проверяет порядок ID.
Для числовых предсказаний указывайте `numeric_columns`, для классификации —
`allowed_values` со списком допустимых меток по столбцам. Без sample порядок ID
проверить невозможно, поэтому используйте шаблон организаторов, когда он есть.

Сохраняйте модели и код в каталоге задачи. Каждый вызов должен завершаться до
выданного бюджета и писать ответ только после сохранения кандидата. API-ключи
не передаются дочернему процессу. Установка пакетов и сеть в ML-модуле не нужны.

`examples/mock_ml_backend.py` — тестовый исполнитель контракта без обучения.
Его нельзя класть в боевой ZIP. Упаковщик включает только корневые `ml_*.py`;
дополнительные ML-модули называйте с этим префиксом. Вложенные пакеты платформа
не переносит.
