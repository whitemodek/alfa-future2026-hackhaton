# AutoML Agent

## Назначение

Автономное решение табличных задач регрессии и классификации. Система получает
условие и данные, выбирает валидацию, сравнивает модели и формирует `submission.csv`.
LLM-оркестратор управляет дополнительными экспериментами через ограниченный набор
инструментов. Типовые операции выполняются нативным ML-конвейером.

Поддерживаются CSV, TSV и Parquet, один целевой столбец, метки классов и вероятности.
Основные алгоритмы: CatBoost, LightGBM, XGBoost, Ridge, LogisticRegression и ExtraTrees для классификации.
Линейный кандидат использует разреженные признаки и TF-IDF для обнаруженных текстовых колонок.
Нетабличные задачи требуют
дополнительного кода; их универсальная поддержка не подтверждена.

## Проверенные результаты

Локальные holdout-оценки на предоставленных задачах организаторов:

| Задача | Метрика | Результат | Разбиение | Простой baseline |
|---|---|---:|---|---:|
| Энергопотребление зданий | RMSE ↓ | **37,1659** | Train: периоды1–4; holdout: полный период5 | Средний train-таргет: 56,7994 |
| Тип сетевой атаки, 10 классов | Macro F1 ↑ | **0,656210** | Группы одинаковых векторов признаков не пересекают train/holdout | DummyClassifier(prior): 0,048551 |

Baseline здесь — константная модель, а не конкурирующая AutoML-система.
Оценка получена до полного дообучения; refit использует весь train.
В классификации штатно применяется SqrtBalanced. Oversampling и focal loss
проверены отдельно и не включены без подтверждённого улучшения готового решения.

Holdout многократно использовался при разработке: риск подстройки под валидацию
сохраняется даже при отсутствии прямой утечки. Вклад LLM в качество отдельно
не измерен: итоговые сквозные проверки использовали локальную команду finish
при настоящем обучении ML-моделей. Для ablation нужны нативный конвейер и агент
с LLM при одинаковых данных, ограничениях ресурсов и нескольких seeds.
По уточнению участника: предыдущая отправка получила **729,491**, следующая —
**660,561**. У первой сообщалось место **189/218**. Локальные улучшения не
подтвердились ростом балла. Формула и детализация скрытой оценки недоступны.
Подготовлен отдельный контролируемый вариант с исправлением завершения агента;
его оценка платформой пока неизвестна.
Подробности и ограничения — в [QA_REPORT.md](QA_REPORT.md).

## Интерфейс запуска

Требуется Python 3.12 и библиотеки из предоставленного организаторами
`requirements.txt`. На платформе зависимости устанавливаются заранее;
решение не выполняет установку пакетов во время работы.

Параметры окружения CLI:

| Переменная | Значение |
|---|---|
| `OPENAI_API_KEY` | Ключ доступа к API |
| `OPENAI_BASE_URL` | Адрес совместимого прокси |
| `OPENAI_MODEL` | Идентификатор модели, поддерживаемый прокси |

`OPENAI_API_KEY` и `OPENAI_BASE_URL` обязательны. Для воспроизводимого запуска
`OPENAI_MODEL` следует задавать явно.

```sh
python3 solution.py task.md
```

Код и `task.md` должны находиться в каталоге задачи. Пути входных таблиц
определяются по условию и фактическим файлам. Результат сохраняется в
`submission.csv` рядом с `task.md`; журналы и исходники экспериментов — в `.agent-*`.
Файл `.env` автоматически не загружается и не включается в сборку.

## Конвейер

1. Определение входных файлов, целевого столбца, метрики и схемы ответа.
2. Выбор воспроизводимого временного, группового или случайного holdout.
3. Сохранение baseline, сравнение бустингов и ограниченные по времени опыты ExtraTrees и линейной модели.
4. Проверка ансамблей, исторических признаков временной регрессии и дополнительных экспериментов.
5. Дообучение выбранной конфигурации на полном train при наличии времени.
6. Проверка CSV и атомарная публикация лучшего допустимого результата.

Кандидаты сравниваются только при одинаковой метрике, направлении и `validation_id`.
Повторяющиеся наборы признаков сохраняются в одной группе. При явном переходе test
в будущие периоды валидация использует последние известные периоды.

Каждая модель сохраняет собственную предобработку. Ансамбли оцениваются по
исходным holdout-моделям; дообученные компоненты используются для предсказания test.
Ошибка последующего эксперимента не заменяет ранее принятый результат.
Для ROC-AUC, log loss и average precision требуется вывод вероятностей.

Для повторяющихся сущностей при временной регрессии предусмотрены два кандидата:
смесь с последним прошлым таргетом и XGBoost с причинными лагами. Их ключ можно
задать через `entity_columns`. Автоматическая структурная сигнатура зданий —
эвристика: требуются регион, тип, площадь и год постройки, достаточное покрытие
и низкая доля коллизий. Неполные и неоднозначные ключи не используют историю.
Валидационные ответы не участвуют в построении признаков. Кандидат принимается
только при улучшении прежней оценки на том же разбиении.

## Архитектура

| Модуль | Ответственность |
|---|---|
| `solution.py` | Входная точка платформы |
| `agent.py` | Оркестрация, инструменты, API-бюджеты и финализация |
| `ml_backend.py` | Разбор задачи, общие операции и CatBoost |
| `ml_models.py` | Адаптеры LightGBM/XGBoost/ExtraTrees и предобработка |
| `ml_portfolio.py` | Сравнение моделей, ансамбли и refit |
| `ml_history.py` | Поправка по строго прошлым наблюдениям сущности |
| `ml_lag.py` | Причинные лаги и отдельная модель XGBoost |
| `ml_validation.py` | Разбиение и диагностика валидации |
| `artifacts.py` | Валидация CSV, снимки кандидатов и публикация |
| `process_runner.py` | Дочерние процессы и контроль ресурсов |
| `agent_config.py`, `agent_prompts.py` | Конфигурация и контракт LLM |

## Ресурсы и отказоустойчивость

По умолчанию: общий дедлайн 175 минут, резерв финализации 15 минут,
до 8 потоков и порог памяти дочернего процесса 28 000 МиБ.
Параметры задаются в `agent_config.py` и переопределяются переменными `AGENT_*`.
`AGENT_BOOTSTRAP_SECONDS` и `AGENT_WARMUP_SECONDS` ограничивают стартовые этапы;
нулевое значение отключает соответствующий этап.

API-бюджет действует на один запуск. Суммарный расход повторных запусков:

```sh
python qa/check_tokens.py /path/to/task --max-tokens 80000
```

Отказ настроенного API сохраняет уже проверенный нативный результат.
Портфель атомарно сохраняет законченные улучшения до следующего опыта.
При таймауте или падении следующего опыта агент восстанавливает такой кандидат
с повторной проверкой CSV; реальная причина остановки остаётся в журнале.
При отсутствии допустимого кандидата CLI возвращает ненулевой код.
Дочерний процесс является механизмом контроля ресурсов, а не песочницей;
изоляцию обеспечивает окружение платформы.

## Проверка и сборка

```sh
python -m unittest discover -s tests -v
python pack_solution.py dist/solution.zip
```

Тесты используют локальные заглушки API и не расходуют платные токены.
Сборка содержит только корневые Python-модули и исходный `requirements.txt`.
Данные, модели, ключи, журналы и сторонние пакеты исключены. Окончания строк
и метаданные ZIP нормализованы для воспроизводимости.

`main` содержит исходники, документацию и тесты. Ветка `codex/submission`
содержит только файлы для платформы. Для загрузки используется `dist/solution.zip`
без внешней папки. Самостоятельная отправка на платформу не выполняется.
